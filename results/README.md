# 基于vLLM的LLM推理服务部署与性能分析

在单卡RTX 4090上部署vLLM推理服务，围绕吞吐量、延迟与并发的关系做了一组压测实验，并对压测中出现的一次异常延迟尖峰做了完整的排查、验证、证伪过程。

## 测试环境

| 项目 | 配置 |
|---|---|
| GPU | NVIDIA RTX 4090 (24GB) |
| 模型 | Qwen2.5-1.5B-Instruct |
| 推理框架 | vLLM v0.27.1 |
| 部署模式 | OpenAI兼容API服务，单实例，`gpu-memory-utilization` 默认 |
| 测试工具 | `vllm bench serve`（官方压测CLI） |
| 数据集 | Random数据集，input_len=1024，output_len=128 |
| 服务器 | 实验室内网服务器（与其他任务共用GPU，测试期间确认GPU空闲） |

## 核心机制简述

vLLM相比朴素推理实现的性能优势主要来自两个机制：

- **PagedAttention**：借鉴操作系统虚拟内存分页思想，把KV Cache切分为固定大小的block按需分配，而非为每个请求预留最大长度的连续显存，大幅降低显存碎片化，提升可容纳的并发请求数。本次测试环境下，vLLM启动日志显示：

  ```
  GPU KV cache size: 664,784 tokens
  Maximum concurrency for 32,768 tokens per request: 20.29x
  ```

  即理论上单卡最多可支撑约20个满长度并发请求，这个数字在后文与实测峰值并发做了对照。

- **Continuous Batching**：请求完成后立即让出资源位，空位由等待队列中的新请求动态填充，使GPU始终保持较高利用率，而非等待整批请求全部完成。

## 压测结果

对不同请求速率（RPS）配置下的服务表现进行了压测，结果如下：

| Rate (RPS) | 请求吞吐(req/s) | 输出token吞吐(tok/s) | 峰值并发 | Mean TTFT (ms) | P99 TTFT (ms) | Mean TPOT (ms) |
|---|---|---|---|---|---|---|
| 1 | 0.97 | 124.07 | 4 | 28.80 | 52.60 | 4.88 |
| 5 | 4.68 | 599.05 | 12 | 20.56 | 25.78 | 5.24 |
| 10 | 9.34 | 1195.83 | 28 | 34.99 | 69.74 | 5.87 |
| 20 | 18.58 | 2378.47 | 46 | 37.47 | 105.80 | 6.85 |

> rate=5的数据取自复测（异常排查过程见下），未出现异常的正常数据代表该配置的真实表现。

![benchmark结果图](results/throughput_chart.png)

**观察结论：**

- 请求吞吐量和token吞吐量随并发配置基本呈线性增长，在测试范围内（RPS 1-20）未观察到明显的吞吐瓶颈，说明Continuous Batching有效地把提升的并发请求转化为了吞吐提升。
- TTFT和TPOT随并发上升有小幅增长（TTFT从约29ms涨到约37ms，TPOT从约4.9ms涨到约6.9ms），符合预期——并发越高，单个请求在调度队列中的等待与批处理内的资源竞争会略微增加延迟，但增幅在可接受范围内，未出现台阶式劣化。
- 峰值并发请求数（rate=20时达到46）已经超过了启动日志给出的理论值20.29——这是因为理论值是按每个请求占满32768 token上下文长度估算的，而实际测试中每个请求仅用了1024 tokens的输入长度和128 tokens的输出长度，实际显存占用远小于理论最坏情况，因此能容纳更多并发。这也说明了PagedAttention"按需分配"而非"按最坏情况预留"的实际收益。

## 一次异常延迟的排查过程

在rate=5的**首次**测试中，观察到一组反常数据：

| 指标 | 数值 |
|---|---|
| Mean TTFT | 212.50 ms |
| Median TTFT | 37.11 ms |
| P99 TTFT | 4539.31 ms |

Mean和P99被大幅拉高，但Median依然正常，说明并非整体系统性变慢，而是极少数请求出现了严重延迟，拖累了平均值和尾部分位数。

**假设1：CUDA kernel首次JIT编译导致的确定性延迟。** vLLM对部分batch size对应的kernel采用懒加载策略，首次遇到某个并发规模时可能触发运行时编译，导致恰好撞上编译过程的请求出现额外停顿。当时的测试顺序恰好是rate=5首次将并发推高到两位数（peak concurrent=12），与该假设的触发条件吻合。

**验证方式：** 完全重启服务（回到冷启动状态），不做任何预热，直接以rate=5发起测试。若假设成立，该规模的kernel编译应必然在此次首测中被再次触发，异常应当复现。

**验证结果：** 异常未复现，TTFT各项指标均恢复正常水平。**假设1被证伪。**

**进一步验证：** 连续重复5次相同配置（rate=5）的测试，观测P99 TTFT的稳定性：

```
27.94 ms / 24.57 ms / 24.43 ms / 24.65 ms / 24.26 ms
```

5次结果全部稳定落在24-28ms区间，复现率0/5，未再出现类似尖峰。

**结论：** 排除了vLLM内部机制导致的确定性延迟解释，判定该异常为一次性的系统层面偶发噪声（可能来源包括共享服务器上其他进程的瞬时资源抢占、Python垃圾回收停顿等非确定性因素），而非vLLM本身在该并发规模下的固有行为。

这一排查过程说明了压测数据中孤立异常点的处理方法论：**观察异常 → 提出机制层面假设 → 设计对照实验验证 → 假设被证伪则修正结论 → 重复实验确认稳定性**，而非直接采信单次测量结果或简单归因。
